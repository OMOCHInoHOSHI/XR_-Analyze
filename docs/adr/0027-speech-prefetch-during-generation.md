# ADR-0027: 読み上げ音声は鑑定文の生成中に先読みして合成する

- ステータス: 承認済み
- 記録日: 2026-08-30
- 関連: [ADR-0002](0002-detection-streaming-contract.md), [ADR-0024](0024-llm-object-explanation.md), [ADR-0025](0025-inspector-voice-readout.md), [ADR-0026](0026-voicevox-character-voice.md)

## 文脈

[ADR-0026](0026-voicevox-character-voice.md) で読み上げを VOICEVOX に移したことで
声は人物像に合うようになったが、待ち時間が伸びた。鑑定文の生成が実測 7.5 秒
([ADR-0024](0024-llm-object-explanation.md))、その**後から** VOICEVOX の合成が
1.3〜2.9 秒 ([ADR-0026](0026-voicevox-character-voice.md)) 走る。固定してから声が
出るまで 10 秒近くかかり、文字が出てからも数秒黙ったままになる。

待ちの正体は「生成 → 合成」を直列に積んでいることである。合成は文が確定しないと
始められないが、**全文が確定するまで待つ必要はない**。一文目が書き終わった時点で、
その一文の合成は始められる。

## 決定

- `/explain` は Ollama を **`stream: true`** で呼び、応答を逐次受け取る。
- **一文が確定するたびに** (`。` `！` `？` `!` `?` と改行で区切る)、その文を
  VOICEVOX へ投げて合成を始める。合成は**別スレッド**で進め、`/explain` の
  レスポンスは文が揃い次第すぐ返す。
- 文ごとの WAV は stdlib の `wave` で **1 つに結合**し、ラベルをキーに
  `_speak_cache` へ入れる。
- `/speak` は、そのラベルの合成が進行中なら**完了を待ってから**返す。先読みが
  働かなかった場合は、従来どおりその場で合成する (退避路)。
- **`/explain` と `/speak` の外部契約 (リクエスト/レスポンスの形) は変えない。**
  この高速化のためにフロントへ加える変更は無い (同じ変更の束に含まれる
  [ADR-0028](0028-readout-holds-the-target.md) 等では別の理由でフロントを触っている)。

## 理由

- **合成を生成の裏に隠した**: 待ち時間を「生成のあとに足す」形から「生成に重ねる」
  形へ変えた。LLM が一文目を書き終えるのは全文完成よりずっと早いので、そこから
  合成を始められる。削れるのは合成時間そのものではなく、それが**見えている時間**
  である。重ねられるのは生成時間の分までなので、合成が生成より長ければ差は残る
  (実際に残っている。下記「結果」を参照)。
- **契約を変えずサーバ内部で完結させた**: フロントに手を入れずに済み、
  [ADR-0002](0002-detection-streaming-contract.md) の「配信側が契約を持つ」形も
  保たれる。Web・Unity・Android のどのクライアントから読んでも同じように速くなる。
- **句点で切った (読点でなく)**: VOICEVOX の `/audio_query` は渡された文の単位で
  抑揚を組み立てる。読点で切ると文の途中で抑揚が切れて不自然になる。句点なら
  文として完結しているため、繋いでも読み上げの調子が壊れない。
- **一文目だけ先に鳴らす案は採らなかった**: 待ちは最短になるが、フロントが複数の
  音声を順に鳴らす実装を持つことになり、文の切れ目で間が空く。無口な鑑定士が
  一息に言い切るほうが人物像 ([ADR-0024](0024-llm-object-explanation.md)) に合う。
- **サーバ側で結合した**: クライアントが受け取る音声は 1 つのままにする。
  `/speak` の「1 ラベル = 1 音声」という単純さを保てば、フロントの再生・停止・
  世代管理 ([ADR-0025](0025-inspector-voice-readout.md)) をそのまま使える。
- **退避路を残した**: 説明文がキャッシュに載っていて `/explain` を通らない場合や、
  先読みが間に合わなかった場合でも、`/speak` はその場で合成して必ず音を返す。

## 結果

- 鑑定文が画面に出てから声が鳴るまでの待ちが、同一条件の実測で
  **2.0〜3.0 秒 (27〜34%) 短くなった**。計測は本番と同じ条件 —
  `backend.server` が YOLO 推論で CPU を使い、load average が 6〜7 ある状態 —
  で、**同じ鑑定文に対して「先読みあり」と「その場で合成」を続けて測り、
  1 件ずつ対にして比べた**もの:

  | 対象 | 先読みあり | その場で合成 | 差 |
  |---|---|---|---|
  | umbrella (73字) | 5.88 秒 | 8.90 秒 | -3.02 秒 (34%) |
  | clock (74字) | 6.78 秒 | 9.59 秒 | -2.81 秒 (29%) |
  | chair (52字) | 5.42 秒 | 7.45 秒 | -2.03 秒 (27%) |
- **引き受けた制約**: **待ちはゼロにならない。** 合成の総コストが鑑定文の生成時間を
  上回るため、生成が終わっても合成は終わっていない。実測では生成 6.9〜8.3 秒に対し、
  合成の総量が 7.5〜9.6 秒ある。重ねられるのは生成時間の分までで、はみ出した分が
  待ちとして残る。ゼロに近づけるには、合成を速くするか鑑定文を短くするしかない。
- **引き受けた制約**: **文に分けると合成の総量が増える。** 同じ 76 字の文を、
  全文一括なら 10.7 秒で合成できるのに対し、3 文に分けると 16.0 秒かかった
  (`/audio_query` と `/synthesis` の往復が文の数だけ増えるため)。それでも
  「生成と重ねられる」利得のほうが大きいので分割を採っているが、分割を細かく
  するほど得になるわけではない。
- **引き受けた制約**: 合成の完了を待つ `/speak` は、その間スレッドプールのスレッドを
  1 本占める。読み上げは同時に 1 つしか走らないため実害は小さい。
- **引き受けた制約**: 同一ラベルの 2 回目以降は `_explain_cache` が効いて `/explain`
  が LLM を呼ばないため、先読みも走らない。音声も `_speak_cache` に残っていれば
  即座に返るが、**こちらは 32 件の LRU なので追い出されている場合がある**
  ([ADR-0025](0025-inspector-voice-readout.md))。鑑定文のキャッシュは上限が無く、
  音声のキャッシュだけが先に溢れるため、「文はキャッシュから即出るのに声だけ
  待たされる」状態は起こりうる。その場合は退避路のその場合成に落ちる。
- **引き受けた制約**: Ollama の NDJSON ストリーミング形式に依存する。応答形式が
  変われば `_ollama_explain` の受信部を直す必要がある。
- **引き受けた制約**: 先読みが走っても、合成が終わる前に窓を閉じれば無駄になる。
  捨てるだけで害はないが、CPU は使っている。
