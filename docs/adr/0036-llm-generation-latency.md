# ADR-0036: 鑑定文生成の待ち時間を詰める (常駐 / MLXモデル / プロンプト短縮)

- ステータス: 承認済み
- 記録日: 2026-09-16
- 関連: [ADR-0024](0024-llm-object-explanation.md), [ADR-0027](0027-speech-prefetch-during-generation.md), [ADR-0033](0033-readout-wait-is-shown.md)

## 文脈

[ADR-0024](0024-llm-object-explanation.md) で鑑定文をローカルLLM
(`gemma4:e4b` / Ollama) で生成し、[ADR-0027](0027-speech-prefetch-during-generation.md) /
[ADR-0033](0033-readout-wait-is-shown.md) で待ちの見せ方を整えた。しかし**生成そのものの
待ち時間**は残っており、speed の実測 (Apple M4 / 24GB, Ollama 0.33.2) で次が分かった。

- **モデル未ロードからの1回目は合計20〜27秒**。内訳はロードが12〜19秒で支配的。
  既定の `keep_alive` は5分なので、鑑定の間隔が空くたびにこれを払う。
- ウォーム時は prefill 224トークンに約3.3秒 (66〜78 tok/s)、decode は
  35〜50トークンに約5秒 (8 tok/s)。合計 8〜10秒。
- **同一プロンプトなら KV キャッシュが効き** prefill は 0.3秒 になるが、
  ラベルが変わるとキャッシュが効かない (プロンプトの物体名が2行目にある)。
- 初回ロード直後のセッションでは decode が 8 tok/s まで落ち、以後のセッションでは
  23〜38 tok/s に回復する事象を観測した (原因は未特定。mmap のページ常駐状態が
  疑わしいが、断定はできない)。
- `EXPLAIN_TIMEOUT_SEC` は 30秒で、コールド最悪 26.9秒と余裕が薄かった。

## 決定

- `OLLAMA_KEEP_ALIVE`(新設) を **30分** にし、モデルを GPU メモリに常駐させる。
- Apple Silicon では **MLX エンジン版 `gemma4:e4b-mlx` を既定モデル**にする
  (プラットフォーム判定。`OLLAMA_MODEL` で上書き可)。
- プロンプトを **224 → 165トークンに短縮**する (判定ルールは削らない)。
- `num_predict` を 150 → **80** にする。
- `EXPLAIN_TIMEOUT_SEC` の既定を 30 → **60秒** にする。

## 理由

- **keep_alive 30分**: 未ロード 12〜19秒は最も大きい待ちである。24GB に 9.6GB を
  常駐させるのは YOLO (MPS) と VOICEVOX と同居できる範囲で、「使い続けている間は
  速い・放置したら解放」の折衷。`ollama ps` で 30分の常駐を確認した。
- **MLX 版を既定に**: 同一条件の実測で prefill が約3倍 (e4b 240 t/s → mlx 717〜754 t/s)、
  ウォーム時の合計が 2.5〜3.3秒 → 1.7〜2.3秒 になった。量子化は nvfp4 で
  Q4_K_M と同じ 4bit。境界物体を含む12ラベルで出力品質は既存と同等以上だった。
  MLX は Apple Silicon 専用のため、それ以外の環境は従来どおり `gemma4:e4b` を使う
  (Windows などで MLX タグは動かない)。低速事象 (8 tok/s) も MLX では未観測。
  なお MLX 版は `ollama pull gemma4:e4b-mlx` が別途必要 (Ollama 0.31.0 以降)。
- **プロンプト短縮**: 3案 (現行 / 短縮 / 短縮+ルール保持) を境界物体6ラベル
  (時計・眼鏡・バナナ・車・はさみ・カップ) と代表4ラベルで A/B した。判定ルール
  (素直に鑑定 / 遺物として扱う) の遵守に差は出ず、文数・装飾なしも維持された。
  短縮版は「過度な神秘化はしない」「畏怖を交えて」という
  [ADR-0024](0024-llm-object-explanation.md) で意味のあるルールを保持する。
  物体名を末尾へ移す案は KV キャッシュの再利用を狙ったが、実測で優位が無かったため不採用。
- **num_predict 80**: 実測の鑑定文は 35〜70トークン。上限を下げると暴走時の待ち
  (150トークン × 低速時 8 tok/s ≒ 19秒) を bound できる。通常時は影響しない。
- **タイムアウト60秒**: コールド最悪 27秒 + 余裕。切れると 503 になり、待つより悪い。

## 結果

- ウォーム時の新規ラベルは実測 **約2秒** (MLX)。キャッシュ済みラベルは従来どおり即時。
- コールド (30分以上放置後) はロードが 5〜19秒残る。ロード直後のセッションで
  decode が落ちる事象は、常駐 (keep_alive) が実質の緩和策になっている。
- **引き受けた制約**: 30分の常駐で 8.5〜9.5GB を GPU メモリに置く。
  メモリを返したい場合は `OLLAMA_KEEP_ALIVE=0` で従来動作に戻せる。
- **引き受けた制約**: MLX エンジンは Ollama 側で新しい扱いのため、不具合が
  あれば `OLLAMA_MODEL=gemma4:e4b` で llama.cpp 版に戻す。プロンプト・
  keep_alive・num_predict は両エンジンで効くことを確認済み。
- 計測スクリプトは一時領域で実行し、リポジトリには置いていない。再測する場合は
  `ollama run --verbose` か `/api/chat` の `load_duration` / `prompt_eval_duration` /
  `eval_duration` を読む。
- 次段の候補: E2B (`gemma4:e2b`) は汎用ベンチで品質差が大きいため (MMLU Pro
  60.0 vs 69.4)、MLX で速度が確保できた現状では優先度を下げる。必要になったら
  `OLLAMA_MODEL=gemma4:e2b` で同じ A/B を回す。蒸留 (E4Bを教師にE2Bを調整) は
  さらに工数が大きいので、実測で不足が出てから検討する。
