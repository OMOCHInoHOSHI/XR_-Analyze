# ADR-0039: 読み上げ音声をディスクへ永続化する

- ステータス: 承認済み
- 記録日: 2026-09-20
- 関連: [ADR-0025](0025-inspector-voice-readout.md), [ADR-0026](0026-voicevox-character-voice.md), [ADR-0027](0027-speech-prefetch-during-generation.md)

## 文脈

[ADR-0025](0025-inspector-voice-readout.md) で読み上げ音声(WAV)のキャッシュを
`server.py` の `_speak_cache`(label → WAV、32件のプロセス内LRU)として持つように
した。[ADR-0027](0027-speech-prefetch-during-generation.md) では鑑定文の生成中に
先読み合成する経路を足したが、結果を格納する先は同じ `_speak_cache` である。

このキャッシュはプロセス内にしか無く、サーバを再起動すると消える。合成には
VOICEVOX で1件あたり実測1.3〜2.9秒([ADR-0026](0026-voicevox-character-voice.md))、
文を分けて先読みする場合は総量がさらに増える([ADR-0027](0027-speech-prefetch-during-generation.md))。
再起動のたびに全ラベル分を作り直すのは無駄が大きく、また事前に読み上げ音声を
まとめて用意しておきたい場面(デモ前の準備など)にも対応できない。

## 決定

- 合成済みWAVをディスクへ永続化するキャッシュ層 `backend/speak_cache.py` を追加する。
  保存先は `config.SPEAK_CACHE_DIR`(既定: リポジトリ直下 `speak_cache/`。空文字で無効)。
- ファイル名は **`{ラベル}-{本文のsha1先頭10桁}.wav`** とする。
- `/speak` は、メモリキャッシュ (`_speak_cache`) にヒットしなければ次にディスクの
  永続キャッシュを試し、それでも無ければ従来どおり先読み結果を待つ/その場で
  合成する(退避路)。新たに合成した結果(退避路・先読みの締め処理の両方)は
  ディスクにも書く。
- 事前にまとめて合成しておく `backend/precompute_speak.py` を追加する。
  鑑定文は別途永続化される `explain_cache.json`(`{label: text}`。並行実装中の
  別機能)を読み、`speak_cache.store` へ書き込む。

## 理由

- **キーに本文のハッシュを含めた**: 鑑定文はラベルだけで決まらない
  ([ADR-0024](0024-llm-object-explanation.md) のプロンプトはラベル固定だが、
  モデルやプロンプトを変えれば同じラベルでも文面が変わりうる)。ラベルだけを
  キーにすると、鑑定文が更新されたときに古い音声が本文とズレたまま再生され
  続けてしまう。これは「文字は新しいのに声が古い」という利用者から見て
  最も気付きにくい壊れ方であり、避けるためにファイル名へ本文のハッシュを
  含めて「本文が変われば別ファイル」を保証した。ファイル名にラベルも残すのは
  人がディレクトリを見たときに中身を推測できるようにするためで、ハッシュだけ
  にすると事前合成の進捗確認などがしづらくなる。
- **WAVのまま保存した(圧縮しない)**: `/speak` は `audio/wav` を返す契約
  ([ADR-0025](0025-inspector-voice-readout.md))で、ディスクの形式をそのまま
  レスポンスに使えれば変換コストが無い。依存を増やさない方針(stdlib のみ)も
  合わせると、mp3/opus 等への圧縮は追加ライブラリか外部コマンドが要る。
  COCO 80クラス程度なら数十MBに収まる見込みで、圧縮の必要性が薄い。将来
  語彙が LVIS 規模(1200+)まで増えて容量が問題になった場合の選択肢として
  圧縮は残すが、今回は採用しない。
- **`.gitignore` に加えた**: 音声はバイナリで1件あたり数百KB〜1MB程度あり、
  `*.mlpackage` と同様に「再生成可能・大きい・機材やモデル設定に依存しうる」
  成果物である。リポジトリに含めるとクローンのたびに無駄な転送が発生するため、
  各自の環境で `precompute_speak.py` を実行して用意する運用にする。
- **事前合成スクリプトを鑑定文のJSONに依存させた**: 鑑定文自体の生成・
  永続化は別ブランチで並行実装中であり、本ADRのスコープではない。
  `--explain-json` で読み込むだけの薄い依存に留め、設定名も共有しないことで
  両ブランチの結合を最小限にした。

## 結果

- サーバを再起動しても、ディスクにあるラベル・本文の組み合わせなら合成
  待ちが発生しない。プロセス内LRU(32件)を超える語彙数でも、ディスクには
  上限を設けていないため取りこぼさない。
- **容量の実測 (2026-09-20、COCO 80 + LVIS 9 の 89件)**: 合計 63MB、1件平均 719KB、
  音声長 平均 15.3秒 (最短 10.0 / 最長 22.7)。VOICEVOX の既定 (24kHz/16bit/mono)
  で、鑑定文 1件 (平均 85字) あたり 0.5〜0.9MB という事前の見積もりどおり。
  この単価では LVIS 1203 語まで揃えると約 0.85GB になる。
- **YOLOE-pf の実行時語彙 1054 語ぶんの実測 (2026-09-22)**: 合計 803MB、1件平均 762KB、
  音声長 平均 15.9秒 (最短 8.4 / 最長 24.7)。壊れた WAV は 0件。`speak_cache/` 全体
  では実行時に出ない語の分も含めて 1074 ファイル・817MB。既定設定でサーバを起動し
  `/explain` → `/speak` を呼ぶと、キャッシュ済みラベルは 2〜5ms、未キャッシュの
  ラベルは 32秒 + 15秒 (モデル未ロードからの生成 + 合成) だった。
- **ENGINE の一過性の応答不良**: 連続合成 500件目で VOICEVOX が壊れた HTTP 応答
  (`http.client.BadStatusLine`) を一度だけ返した。`tts._voicevox` が `URLError` 系
  しか `TTSUnavailable` に変換していなかったため例外が素通りしてバッチが落ちた。
  同じ穴は `/speak` の退避路でも 500 になるので、`HTTPException` 系も
  `TTSUnavailable` にまとめ、バッチは 5秒おいて 2回まで再試行してから中断する
  ようにした。
- **合成時間の実測**: 単独では 1件 5〜10秒だが、LLM の事前生成 (Ollama) と並走
  させると平均 23秒・最大 38秒まで伸びた。`TTS_TIMEOUT_SEC` の既定 20秒は対話
  用の値で、この条件では 8件目で超過して `precompute_speak` が中断した。
  バッチで並走させるときは `TTS_TIMEOUT_SEC=120` 程度に伸ばす必要がある
  (再実行すれば既存分はスキップされ、続きから合成される)。
- **引き受けた制約**: ディスクに上限が無いため、語彙が非常に大きい構成
  (LVIS等)では際限なく増える。将来的に容量が問題になれば、古いファイルの
  掃除やLRU化、圧縮形式への移行を検討する必要がある。
- **引き受けた制約**: 鑑定文の永続キャッシュ(`explain_cache.json`、別ブランチ)
  と本キャッシュは独立に存在する。鑑定文の生成方法(プロンプト・モデル)を
  変えて `explain_cache.json` を作り直しても、本キャッシュのファイルは
  本文のハッシュが変わるため自動的に無効化される(=再合成が必要になる)。
  古いファイルは自動では消えないため、大きく作り直す場合は `speak_cache/`
  を手動で空にすることを推奨する。
