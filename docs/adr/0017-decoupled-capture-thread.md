# ADR-0017: カメラ取得を推論から切り離し、専用スレッドで回す

- ステータス: 承認済み
- 記録日: 2026-08-27
- 関連: [ADR-0006](0006-single-background-pipeline.md), [ADR-0007](0007-viewport-crop-calibration.md), [ADR-0016](0016-mask-free-fast-inference.md)

## 文脈

[ADR-0006](0006-single-background-pipeline.md) では取得と推論を 1 本の背景スレッドで
回していた。推論が 1 フレーム 30ms 程度なら問題にならないが、
`yoloe-11l-seg-pf.pt` では 150-250ms かかる。この差で次の問題が出る。

- 推論の間カメラは読まれない。`CAP_PROP_BUFFERSIZE` はバックエンドによっては
  無視されるため、次の `read()` はドライバのキューに溜まった**古いフレーム**を返す。
  AR 表示では表示遅延がそのまま体感になる。
- キューが空だと `read()` が最大 1/CAM_FPS 秒ブロックし、その間 GPU が遊ぶ。
- 向き補正 (`cv2.flip`) と切り抜きは、推論に使わず捨てるフレームにも掛かっていた。

## 決定

- `Pipeline` を **取得スレッドと推論スレッドの 2 本**にする。取得スレッドは
  カメラを回し続け、**最新の生フレーム 1 枚だけ**を受け渡し口に置く。古い分は捨てる。
- 向き補正と切り抜きは、**実際に推論するフレームにだけ**掛ける。
  `Camera` は `grab()` (生フレーム) と `transform()` (補正) に分け、
  従来の `read()` は両者を呼ぶだけにして既存の呼び出し元をそのまま動かす。
- `MAX_DET` の絞り込みは `Detector` 側へ移した ([ADR-0016](0016-mask-free-fast-inference.md))。

## 理由

- **最新の 1 枚だけを持つ方針は変えていない**: [ADR-0006](0006-single-background-pipeline.md)
  の「遅れたフレームを配信しても価値が無い」という判断はそのまま正しい。
  変えたのは「1 本のスレッドで回す」という実装の部分だけである。キューを持たず
  上書きするので、スレッドを増やしても遅延は伸びない。
- **補正を推論側に寄せる**: カメラ 30fps に対し推論は 4-7fps なので、
  補正の 8 割方は捨てるフレームに掛かっていた。`transform()` を推論スレッドが
  呼ぶことで、`_out_size` の書き手も 1 本のままである。
- **待ち合わせに `Event` を使う**: ポーリングで `sleep` を挟むと、その分だけ
  最新フレームの取得が遅れる。停止時は `Event` を立てて推論スレッドを起こす。

## 結果

- 推論スレッドはカメラ待ちで止まらず、常に**最新のフレーム**を推論する。
  ドライバのキューに溜まった古いフレームを推論することが無くなった。
- スレッドが 1 本増える。取得スレッドの実質的な仕事は `cap.read()` だけで、
  その中では GIL が解放されるため推論を妨げない。
- 副次的に `/ws` と MJPEG の無駄も削った。検出 JSON にフレーム画素は要らないのに
  `snapshot()` がフレームを毎回コピーしていたのをやめ、MJPEG は `frame_id` が
  変わったときだけ再エンコードするようにした。推論 fps が `STREAM_FPS` より低いと、
  それまでは同じ絵を何度も JPEG に焼き直していた。
