# ADR-0038: 鑑定文キャッシュをディスクに永続化し、事前生成する

- ステータス: 承認済み
- 記録日: 2026-09-20
- 関連: [ADR-0024](0024-llm-object-explanation.md), [ADR-0036](0036-llm-generation-latency.md)

## 文脈

[ADR-0024](0024-llm-object-explanation.md) で鑑定文をローカルLLM (Ollama) から
生成する方式にし、[ADR-0036](0036-llm-generation-latency.md) の実測で、常駐
(keep_alive) とMLXエンジンにより**ウォーム時でも新規ラベルの生成に約2秒**
かかることが分かった。decode(35〜70トークンの出力)が支配的で、これ以上は
プロンプト短縮や `num_predict` の調整では詰めきれない。

一方で `_explain_cache` は `server.py` のプロセス内 dict でしかなく、サーバを
再起動するたびに空になる。検出できるラベルは検出モデルの語彙で決まり
(yolov8 なら COCO 80、YOLOE-pf なら `VOCAB=auto` で LVIS に絞った 1054 語。
[ADR-0018](0018-vocabulary-restriction.md))、**語彙が有限**である。つまり全ラベル分をあらかじめ
生成しておけば、実運用中は「初めて見るラベル」以外は生成コストがゼロになる。

## 決定

- 鑑定文キャッシュ (`label -> text`) をJSONファイル (`EXPLAIN_CACHE_PATH`、既定
  はプロジェクトルート直下の `explain_cache.json`) へ永続化する。
- サーバは起動時にこのファイルを読み込み `_explain_cache` の初期値にする。
  `/explain` で新規生成したラベルは、生成直後に同じファイルへ書き戻す。
- 生成ロジックを `backend/server.py` から `backend/explain.py` へ切り出し、
  事前生成専用のバッチ `backend/precompute_explain.py`
  (`python3 -m backend.precompute_explain`) から同じ `generate()` を呼べるようにする。
- `explain_cache.json` はコミット対象とする(生成物だが、利用者が Ollama を
  何十分も回さずに済むようにするため)。

## 理由

- **JSON + stdlibのみ**: `calib_store.py` (ADR-0008) と同じ「アトミック書き込み
  (tmpファイル→`os.replace`)」の流儀に揃え、新規依存を増やさない。キーで
  ソートして保存するのは、`git diff` で追加・変更されたラベルが分かりやすい
  ようにするため(差分レビューのしやすさを優先し、`indent=0`ではなく
  `indent=2`にした)。
- **事前生成の対象は「設定中のモデルが実際に出すラベル」にする** (`vocab.runtime_labels`。
  `MODEL` / `CLASSES` / `VOCAB` を detector と同じ手順で解決する)。`/explain` に
  届くのはモデル語彙の名前そのものであり、LVIS の見出し語とは呼び名が違う語が
  ある (LVIS "aerosol can" / モデル "spray can")。実際に対訳辞書の見出し語 1203 語で
  生成したところ、YOLOE-pf の実行時語彙 1054 語のうち 163 語を取り逃がし、322 語は
  実行時に出ない語だった。サーバと同じ環境変数で回せば取り逃がしが無い。
- **コミット対象にする**: 事前生成には Ollama で 1000 語級を
  回す必要があり(ウォーム時1件約2秒でも1203件なら数十分)、利用者ごとに
  毎回これを強いるのは非現実的。生成済みJSONを共有すれば、初回セットアップの
  Ollama起動だけで新規ラベル以外は即時表示になる。
- **生成ロジックの切り出し**: サーバ本体(`server.py`)と事前生成バッチが同じ
  `explain.generate()` を呼ぶことで、プロンプトやストリーミング処理の実装が
  二重化しない。プロンプトを変更したら、サーバ内キャッシュ・永続キャッシュの
  文体が古いプロンプトのまま残る。**プロンプト変更時は
  `explain_cache.json` の再生成が必要**という制約を引き受ける(バージョニングは
  今回のスコープでは持たない)。

## 結果

- 事前生成済みのラベルは、サーバ再起動後も生成コストゼロ(ファイル読み込みのみ)
  で鑑定文が返る。フロントの待ち時間はキャッシュ済みラベルについてはゼロになる。
- 未生成のラベル(事前生成の対象外だったラベルや、LVISで事前生成していない
  語)は従来どおりその場で生成し、その結果もキャッシュへ追記される。
- **引き受けた制約**: プロンプト・モデル・世界観設定を変えたら、
  `explain_cache.json` は既存分すべてが「古い文体」のまま残る。作り直すには
  `--force` 付きで `precompute_explain` を再実行するか、ファイルを削除して
  作り直す必要がある。
- **引き受けた制約**: `EXPLAIN_CACHE_PATH` を空文字にすると永続化を無効化でき、
  従来どおりプロセス内キャッシュのみの挙動に戻せる。
- COCO 80 ラベルを `python3 -m backend.precompute_explain` で生成してコミットした
  (2026-09-20 実測: 80件 / 合計 485.8秒 / 平均 6.1秒/件、21.8KB、平均 85字/件、
  書式違反 0件)。1件 6秒は [ADR-0037](0037-branch-specific-prompt-rejected.md) で
  観測した decode 9.5 tok/s の状態での値で、機械が軽ければ半分程度で済む。
  続けて `--lvis` で LVIS 1203 語 (COCO と重複する 70 語を除いた 1133 件) も生成
  してコミットした (実測: 1133件 / 合計 6787秒 ≒ 1時間53分 / 平均 6.0秒/件。
  キャッシュ総数 1213 件、342KB、平均 88字/件)。
- 生成文の粗い検査 (1213件): 空・英字混じり・見出し/箇条書きは 0件。「現代」という
  語を含むものが 80件 (6.6%) あり、「現代の技術水準から見れば」のように鑑定士の
  視点から外れて読める文が混じる。プロンプトの制約で直すなら、対象ラベルだけ
  `--labels` と `--force` で作り直せばよく、全件の再生成は要らない。
