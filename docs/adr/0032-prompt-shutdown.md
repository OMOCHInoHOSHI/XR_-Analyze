# ADR-0032: 終了は処理中のリクエストを待たずに打ち切る

- ステータス: 承認済み
- 記録日: 2026-08-30
- 関連: [ADR-0006](0006-single-background-pipeline.md), [ADR-0024](0024-llm-object-explanation.md), [ADR-0027](0027-speech-prefetch-during-generation.md)

## 文脈

`Ctrl+C` を押してもサーバがすぐ終わらない、という不満が出た。実測すると:

| 状態 | 終了までの時間 |
|---|---|
| 何もしていない | 0.65 秒 |
| 鑑定文の生成中 | **8.59 秒** |

ログには `Waiting for connections to close. (CTRL+C to force quit)` が出ている。
uvicorn は既定で、**処理中の HTTP リクエストが応答を返し終えるまで待つ**。
`/explain` は鑑定文の生成に最大 `EXPLAIN_TIMEOUT_SEC` (既定 30 秒)、`/speak` は
先読み合成の完了待ちに最大 `TTS_TIMEOUT_SEC` (既定 20 秒) かけうる
([ADR-0027](0027-speech-prefetch-during-generation.md)) ので、間が悪ければ
数十秒待たされる。

## 決定

- uvicorn の **`timeout_graceful_shutdown`** に `SHUTDOWN_GRACE_SEC` (既定 **2.0 秒**、
  環境変数で変更可) を渡し、この時間を過ぎたら処理中のリクエストごと閉じる。

## 理由

- **止めると決めた後の生成結果に用はない**: 鑑定文も読み上げ音声も、画面を閉じた
  あとには誰も受け取らない。応答を返しきるために待つ意味がない。
- **待つ設計が向く処理と向かない処理がある**: 書き込みを伴う処理なら中断が問題に
  なるが、`/explain` と `/speak` はどちらも読み取り専用の生成である。途中で切っても
  壊れるものがない (キャッシュに半端なものが残らないことは
  [ADR-0027](0027-speech-prefetch-during-generation.md) の設計で担保されている)。
- **0 ではなく 2 秒にした**: アプリ側の後始末 — カメラの解放とパイプラインの停止
  ([ADR-0006](0006-single-background-pipeline.md)) — は `lifespan` の終了処理で
  別途走る。実測でアイドル時の終了が 0.65 秒なので、2 秒あれば通常の後始末は
  間に合う。0 にすると余裕がない。
- **環境変数にした**: 遅い機材で後始末が間に合わない場合に伸ばせる。詰まる理由が
  分かっているときに、コードを触らず調整できる。

## 結果

- 鑑定文の生成中でも **0.99 秒**で終了する (8.59 秒から短縮)。何もしていない状態の
  0.66 秒とほぼ変わらない。
- **引き受けた制約**: 終了の瞬間に走っていた `/explain` や `/speak` は、応答を
  返さずに切られる。クライアント側は接続エラーになるが、サーバを止めているので
  実害はない。
- **引き受けた制約**: 後始末が 2 秒を超える環境では、カメラの解放が終わる前に
  プロセスが落ちうる。現状の実測では 1 秒を切っているが、機材が変われば
  `SHUTDOWN_GRACE_SEC` で伸ばす必要がある。
