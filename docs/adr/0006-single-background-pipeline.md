# ADR-0006: 取得と推論を単一の背景スレッドに集約し、最新の1件だけを保持する

- ステータス: 承認済み (スレッド構成のみ [ADR-0017](0017-decoupled-capture-thread.md) で置換)
- 記録日: 2026-08-18
- 関連: [ADR-0002](0002-detection-streaming-contract.md), [ADR-0007](0007-viewport-crop-calibration.md), [ADR-0010](0010-client-side-display-policy.md), [ADR-0016](0016-mask-free-fast-inference.md), [ADR-0017](0017-decoupled-capture-thread.md)

> **後日の変更**: 「取得と推論を 1 本のスレッドで回す」という部分だけは
> [ADR-0017](0017-decoupled-capture-thread.md) で取得スレッドの分離に置き換えた。
> 「最新の 1 件だけを保持する」「調整値にロックを持たない」「推論失敗で止めない」
> という残りの決定はそのまま有効である。`MAX_DET` の絞り込み位置も
> [ADR-0016](0016-mask-free-fast-inference.md) で `Detector` 側へ移した。

## 文脈

カメラ読取と YOLO 推論はどちらも重い。これをリクエスト処理の中で行うと、
WebSocket と MJPEG が同時に繋がるたびに推論が走り、クライアント数に比例して
負荷が増える。ブラウザで `/` と `/video` を同時に開くだけでこの状況になる。

## 決定

- 取得 → 推論を **1 本の背景スレッド (`Pipeline`)** で回し、
  「最新の 1 フレーム」と「最新の検出結果」だけを保持する。
  WebSocket / MJPEG はそれを参照するだけにする。
- フレームと検出結果の受け渡しはロックで守る (`snapshot()` はコピーを返す)。
- 一方、**ズーム / オフセットの調整値はロックを持たない**。
- 推論の失敗はエラーとして記録するだけで、ループは止めない。

## 理由

- **推論を1本にする**: クライアントが何個繋がっても推論コストが増えない。
- **最新だけを保持する**: 遅れたフレームを配信しても AR 表示では価値が無い。
  キューに溜めると遅延が伸び続けるだけになる。
- **調整値にロックを持たない**: 書き込むのはリクエストハンドラのみで、読取ループは
  参照するだけ。仮に更新の途中で読まれても、そのフレームの切り抜き位置が
  1 コマぶん中途半端になるだけで、次のフレームから正しくなる。この程度の不整合に
  ロックのコストと複雑さを払う価値が無い。同じ理由で `Camera` 側も
  `zoom` / `offset_x` / `offset_y` を普通の公開属性として持っている。
- **推論失敗で止めない**: カメラ由来の一時的な失敗でサーバごと落とすと、
  グラスを装着したままの復旧ができない。

## 結果

- 実測 fps は指数移動平均でならして配信する (瞬間値はぶれが大きく読みにくいため)。
- `MAX_DET` による信頼度上位 N 件の絞り込みもこのスレッドで行うため、配信と表示の
  両方に効く。この副作用は [ADR-0010](0010-client-side-display-policy.md) に制約として記録した。
- `/ws` は新しい `frame_id` のときだけ送るため、カメラが止まると配信も止まる。
  フロント側はそれを前提に直近ペイロードで描き直している。
