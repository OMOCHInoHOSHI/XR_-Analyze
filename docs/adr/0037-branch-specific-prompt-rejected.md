# ADR-0037: 分岐別プロンプトは採用しない (出力長が変わらないため)

- ステータス: 承認済み
- 記録日: 2026-09-20
- 関連: [ADR-0024](0024-llm-object-explanation.md), [ADR-0036](0036-llm-generation-latency.md), [ADR-0038](0038-explain-persistent-cache.md), [ADR-0039](0039-speak-persistent-cache.md)

## 文脈

[ADR-0036](0036-llm-generation-latency.md) で鑑定文の生成はウォーム時「約2秒」まで
詰めたが、実使用ではまだ待ちが長いと感じられた。ウォーム時の内訳は prefill が
0.2秒で、残りはほぼ decode (出力トークン数 ÷ 生成速度) である。

現行プロンプトは「昔からの道具は素直に鑑定 / 科学技術の産物は遺物として扱う」の
2ルールを同梱し、どちらに落とすかはモデルが生成の中で暗黙に決めている。
ここで「分岐を先に判定しておき、該当ルールだけを載せた短いプロンプトを渡せば
速くなるか」という案が出た。判定器の候補として、文章を生成せず判断だけを返す
クラウド API (TypeSafe AI の Jev。p50 約240ms、Choice 形式で選択肢ごとの確率と
確信度を返す) も挙がった。

## 決定

- **分岐別プロンプトは採用しない。** プロンプトと生成経路は現行のまま。
- 実行時に外部の判定器 (Jev 等) を挟むこともしない。
- 生成の待ちは、生成そのものを実行時から外す方向 ([ADR-0038](0038-explain-persistent-cache.md) /
  [ADR-0039](0039-speak-persistent-cache.md) の事前生成・永続キャッシュ) で解消する。

## 理由

- **出力トークン数が変わらなかった。** 12ラベル (遺物側6: clock・car・laptop・
  cell phone・tv・remote / 素直側6: banana・scissors・cup・umbrella・chair・book)
  × 2条件 × 3回 = 72回を交互に実行して比べた (`gemma4:e4b-mlx`、temperature 0.4、
  num_predict 80、`backend.server` 停止)。

  | 条件 | 出力トークン 平均 / 中央 | プロンプト | decode 平均 | 合計 平均 | 書式違反 |
  |---|---|---|---|---|---|
  | 現行 (2ルール同梱) | 56.3 / 54 | 166 | 5.44秒 | 5.77秒 | 0 |
  | 分岐別 (判定済みを模す) | 56.8 / 50 | 119 | 5.52秒 | 5.76秒 | 0 |

  分岐ごとに見ると素直側は 45.6 → 42.1 (-8%)、遺物側は 66.9 → 71.5 (+7%) で
  相殺された。prefill の削減は 0.08秒に留まる。分岐の判定は現状、出力に判定
  トークンを出しておらずコストがゼロなので、判定を外に出しても削れるものが無い。
- **判定器を挟むと純増になる。** Jev を実行時に呼ぶとネット往復 240〜300ms が
  待ちに足され、[ADR-0024](0024-llm-object-explanation.md) の「オフライン・
  API 従量課金なし」にも反する。ラベル語彙は有限なので、分岐を固定したいなら
  一度だけ全ラベルを分類して辞書に持てばよく、実行時に呼ぶ理由が無い。
- **decode の速度が [ADR-0036](0036-llm-generation-latency.md) の実測を大きく下回った。**
  72回すべてと、その後の再測12回で decode は 8.5〜12.6 tok/s (平均 9.5〜10.4) に
  留まり、ADR-0036 の MLX 実測 23〜38 tok/s の半分以下だった。計測中の機械は
  物理メモリ 23GB 使用 / 空き 90MB、圧縮 7.3GB、スワップ 22.5GB 中 20.9GB 使用で、
  CPU を占める処理が無いのに load average が 6〜8 あった (ページングで膨らむ)。
  9.9GB のモデルの重み (mmap) がページアウトされ、SSD から読み戻しながら decode
  していると考えるのが自然で、ADR-0036 が「mmap のページ常駐状態が疑わしい」と
  した低速事象と同じ機構と見る。ただしメモリを空けて再測する検証 (他のアプリを
  閉じる必要がある) は行っておらず、断定はしていない。
  この観測から、YOLO・VOICEVOX・ブラウザと同居する実使用では鑑定の待ちが
  「約2秒」ではなく 5〜6秒だった可能性が高い。プロンプトの工夫では届かない差で
  あり、生成を実行時から外すこと (事前生成) と、モデル常駐 (keep_alive 30分・
  9.9GB) を実行時に不要にすることが、待ちにもメモリ圧にも効く。

## 結果

- プロンプトは変更なし。分岐別プロンプトの案はここで閉じる。
- 「A/B は出力トークン数で比べる」という手順が確立した。速度は機械の状態で
  半分以下に振れるが、トークン数は振れないため、プロンプト案の比較指標として
  信頼できる。
- **引き受けた制約**: 境界物体 (時計・眼鏡など) の分岐の揺れ
  ([ADR-0024](0024-llm-object-explanation.md) の制約) はこの決定では解消しない。
  解消したい場合は、実行時判定ではなく事前生成の段階で分岐を固定する
  (全ラベルを一度だけ分類して辞書に持つ) のが筋。
- 計測スクリプトは一時領域で実行し、リポジトリには置いていない
  ([ADR-0036](0036-llm-generation-latency.md) と同じ扱い)。再測する場合は
  `/api/chat` を `stream: false` で呼び、`eval_count` / `eval_duration` /
  `prompt_eval_count` を読む。計測前に `backend.server` を止め、`ollama ps` と
  `sysctl vm.swapusage` でモデルの常駐とスワップの状態を記録しておくこと。
